برنامه‌ای کنسولی به زبان Python که یک نام دامنه را از کاربر می‌گیرد و طبق ترتیب ثابت زیر دربارهٔ آن تصمیم می‌گیرد:

1. دامنه‌های **فهرست تبلیغاتی** را به آدرس بی‌اثر (Sinkhole) هدایت می‌کند (`AD_BLOCK`).
2. دامنه‌های **فهرست تحریم** را به آدرس سرور واسط هدایت می‌کند (`SANCTION`).
3. پاسخ سایر دامنه‌ها را از برنامهٔ جداگانهٔ **Upstream** با پیام متنی روی سوکت UDP می‌گیرد و با رعایت TTL در **کش** نگه می‌دارد (`CACHE` / `UPSTREAM`).

## 1. پیش‌نیازها

- Python نسخهٔ ۳٫۸ یا بالاتر (تست‌شده با نسخه‌های ۳٫۱۲ و ۳٫۱۳)
- هیچ کتابخانهٔ خارجی لازم نیست؛ فقط کتابخانهٔ استاندارد (`socket`، `ipaddress`، `time`، `pathlib`، `datetime`) استفاده شده است.
- دو پنجرهٔ ترمینال (یکی برای Upstream و یکی برای Proxy) که هر دو در پوشهٔ پروژه باز شده باشند.
- نیازی به آرگومان خط فرمان نیست.

## 3. روش اجرا

ترتیب اجرا مهم است: **ابتدا Upstream و سپس Proxy**.

**ترمینال ۱: برنامهٔ Upstream شبیه‌ساز**

```
python upstream_server.py
```

خروجی مورد انتظار:

```
Upstream Server running on 127.0.0.1:5354
```

**ترمینال ۲: برنامهٔ Proxy DNS**

```
python main.py
```

خروجی مورد انتظار:

```
DNS Proxy ready.
Enter domain (or exit or log or stats or cache):
```

سپس نام دامنه را تایپ کنید و Enter بزنید. برای پایان برنامه `exit` را تایپ کنید (بزرگی و کوچکی حروف مهم نیست). برنامهٔ Upstream را با `Ctrl+C` ببندید.

### نمونهٔ اجرا

```
Enter domain (or exit): notads.example.com
Domain : notads.example.com
Source : UPSTREAM
Status : OK
IP : 198.51.100.7
TTL : 5
```

## 4. فایل پیکربندی (`config.txt`)

برنامه هنگام شروع، فایل `config.txt` را از پوشهٔ برنامه می‌خواند (نام فایل ثابت است). هر خط یک تنظیم به شکل `key=value` و بدون فاصله دور علامت `=` است. خط خالی و خطی که با `#` شروع شود نادیده گرفته می‌شود و ترتیب خطوط اهمیتی ندارد.

```
upstream_ip=127.0.0.1
upstream_port=5354
upstream_timeout_sec=2
sinkhole_ip=0.0.0.0
proxy_ip=192.0.2.10
local_ttl=60
ad_list_file=ad_list.txt
sanction_list_file=sanction_list.txt
cache_enabled=true
```

| کلید | نوع | وضعیت | توضیح |
|---|---|---|---|
| `upstream_ip` | IPv4 | الزامی | آدرس IP برنامهٔ Upstream |
| `upstream_port` | عدد (۱ تا ۶۵۵۳۵) | الزامی | پورت UDP برنامهٔ Upstream |
| `upstream_timeout_sec` | عدد مثبت (ثانیه) | پیش‌فرض ۲ | مهلت انتظار برای پاسخ؛ فقط یک تلاش و بدون ارسال مجدد |
| `sinkhole_ip` | IPv4 | الزامی | آدرس پاسخ دامنه‌های تبلیغاتی |
| `proxy_ip` | IPv4 | الزامی | آدرس پاسخ دامنه‌های فهرست تحریم |
| `local_ttl` | عدد صحیح مثبت (ثانیه) | پیش‌فرض ۶۰ | TTL پاسخ‌های Sinkhole و Proxy |
| `ad_list_file` | مسیر فایل | الزامی | فایل فهرست تبلیغاتی |
| `sanction_list_file` | مسیر فایل | الزامی | فایل فهرست تحریم |
| `cache_enabled` | `true` / `false` | پیش‌فرض `true` | روشن یا خاموش بودن کش |

مسیر فایل‌های فهرست نسبت به پوشهٔ برنامه تفسیر می‌شود.

### خطای پیکربندی

اگر `config.txt` یا یکی از دو فایل فهرست پیدا نشود، کلید الزامی وجود نداشته باشد یا مقداری نامعتبر باشد، برنامه پیامی به شکل `Config error: ...` چاپ می‌کند و متوقف می‌شود. این تنها حالتی است که برنامه (به‌جز دستور `exit`) متوقف می‌شود. نمونه:

```
Config error: missing proxy_ip
```

## 5. فایل‌های فهرست

- در هر خط یک دامنه نوشته می‌شود؛ فاصله‌های ابتدا و انتهای خط حذف می‌شود.
- خط خالی و خطی که با `#` شروع شود نادیده گرفته می‌شود.
- هر ورودی نرمال‌سازی می‌شود (حروف کوچک و حذف یک نقطهٔ پایانی). تکراری‌ها یک بار نگه‌داری می‌شوند.
- علامت `*` پشتیبانی نمی‌شود؛ تطبیق زیردامنه به‌صورت خودکار انجام می‌شود.
- خط نامعتبر (مثلاً شامل فاصله در وسط نام) رد می‌شود و هنگام شروع پیام `Warning: bad line in <file>: <line>` چاپ می‌شود؛ برنامه متوقف نمی‌شود.

نمونه:

```
# ad_list.txt
ads.example.com
tracker.example.net
both.example.com
```

```
# sanction_list.txt
service.example.org
both.example.com
```

## 6. ترتیب تصمیم‌گیری و قواعد تطبیق

برای هر خط ورودی، مراحل زیر دقیقاً به همین ترتیب اجرا می‌شود و نتیجهٔ هر مرحله با مراحل بعدی تغییر نمی‌کند:

| گام | بررسی | نتیجه | تماس با Upstream |
|---|---|---|---|
| ۱ | ورودی `exit` | چاپ `Bye.` و پایان برنامه | خیر |
| ۲ | اعتبار ورودی | در صورت نامعتبر بودن: `INVALID_INPUT` | خیر |
| ۳ | نرمال‌سازی نام | فقط آماده‌سازی | خیر |
| ۴ | فهرست تبلیغاتی | `AD_BLOCK` با `sinkhole_ip` | خیر |
| ۵ | فهرست تحریم | `SANCTION` با `proxy_ip` | خیر |
| ۶ | کش محلی | `CACHE` با TTL باقی‌مانده | خیر |
| ۷ | Upstream | `UPSTREAM` با `OK`، `NOT_FOUND` یا `SERVER_ERROR` | بله |

### قاعدهٔ تطبیق دامنه

| ورودی فهرست | نام درخواستی | تطبیق | دلیل |
|---|---|---|---|
| `example.com` | `example.com` | بله | برابر |
| `example.com` | `b.example.com` | بله | زیردامنه |
| `example.com` | `EXAMPLE.COM.` | بله | پس از نرمال‌سازی |
| `example.com` | `notexample.com` | خیر | مرز برچسب رعایت نشده |
| `example.com` | `example.com.org` | خیر | پسوند متفاوت |
| `b.example.com` | `example.com` | خیر | دامنهٔ والد با ورودی زیردامنه تطبیق نمی‌دهد |

## 7. اعتبارسنجی و نرمال‌سازی ورودی

ابتدا فاصله‌های ابتدا و انتهای خط حذف می‌شود. ورودی در این حالت‌ها **معتبر** است:

- خالی نباشد؛
- فقط شامل حروف انگلیسی، رقم، خط تیره (`-`) و نقطه باشد؛
- با نقطه شروع نشود؛
- دو نقطهٔ پشت‌سرهم نداشته باشد (یک نقطه در انتها مجاز است).

علاوه بر قواعد بالا، پیاده‌سازی ما این محدودیت‌های استاندارد DNS را هم بررسی می‌کند: طول هر برچسب حداکثر ۶۳ نویسه، طول کل نام حداکثر ۲۵۳ نویسه، و هیچ برچسبی با خط تیره شروع یا تمام نمی‌شود.

هر ورودی دیگر `INVALID_INPUT` است. **نرمال‌سازی** یعنی تبدیل به حروف کوچک و حذف یک نقطهٔ پایانی؛ نام چاپ‌شده در خط `Domain` همیشه نرمال‌شده است (برای ورودی خالی عبارت `(empty)` چاپ می‌شود).

## 8. قالب خروجی

برای هر ورودی غیر از `exit`، دقیقاً یک بلوک پنج‌خطی و سپس یک خط خالی چاپ می‌شود:

```
Domain : <normalized name>
Source : AD_BLOCK | SANCTION | CACHE | UPSTREAM | NONE
Status : OK | NOT_FOUND | SERVER_ERROR | INVALID_INPUT
IP : <ip address> or -
TTL : <seconds> or -
```

| وضعیت | Source | Status | IP | TTL |
|---|---|---|---|---|
| دامنه در فهرست تبلیغاتی | `AD_BLOCK` | `OK` | `sinkhole_ip` | `local_ttl` |
| دامنه در فهرست تحریم | `SANCTION` | `OK` | `proxy_ip` | `local_ttl` |
| پاسخ معتبر در کش | `CACHE` | `OK` | IP ذخیره‌شده | ثانیه‌های باقی‌مانده (حداقل ۱) |
| پاسخ `OK` از Upstream | `UPSTREAM` | `OK` | IP پاسخ | TTL پاسخ |
| پاسخ `NOT_FOUND` از Upstream | `UPSTREAM` | `NOT_FOUND` | `-` | `-` |
| بدون پاسخ تا پایان مهلت یا پاسخ نامفهوم | `UPSTREAM` | `SERVER_ERROR` | `-` | `-` |
| ورودی نامعتبر یا خالی | `NONE` | `INVALID_INPUT` | `-` | `-` |

## 9. ارتباط با Upstream

ارتباط فقط با سوکت UDP خام و پیام‌های متنی انجام می‌شود (بدون هیچ کتابخانهٔ DNS):

1. ساخت یک سوکت UDP (`AF_INET`، `SOCK_DGRAM`)؛
2. تنظیم مهلت انتظار برابر `upstream_timeout_sec`؛
3. ارسال پیام `QUERY <domain>` به `(upstream_ip, upstream_port)`؛
4. انتظار برای پاسخ (بافر دریافت ۱۰۲۴ بایت)؛ در صورت پایان مهلت یا بروز خطا نتیجه `SERVER_ERROR` است و **تلاش مجدد انجام نمی‌شود**؛
5. تفسیر پاسخ: `OK <ip> <ttl>` یا `NOT_FOUND`؛ هر پاسخ دیگری `SERVER_ERROR` است؛
6. بستن سوکت.

نمونهٔ پیام‌ها:

```
Proxy    -> Upstream : QUERY normal.example.net
Upstream -> Proxy    : OK 198.51.100.7 5

Proxy    -> Upstream : QUERY missing.example.net
Upstream -> Proxy    : NOT_FOUND
```

### Upstream شبیه‌ساز

- روی `127.0.0.1` و پورت `5354` گوش می‌دهد (در این برنامه مقدار ثابت است).
- برای هر دامنه به‌جز `missing.example.net` پاسخ `OK 198.51.100.7 5` می‌دهد.
- برای `missing.example.net` پاسخ `NOT_FOUND` می‌دهد.
- برای هر پیام یک خط `Request #N: <domain> -> <reply>` در کنسول خودش چاپ می‌کند (`N` از ۱ شروع می‌شود). با این خط‌ها مشخص می‌شود Proxy به Upstream مراجعه کرده است یا نه.

```
Request #1: normal.example.net -> OK 198.51.100.7 5
Request #2: missing.example.net -> NOT_FOUND
```

## 10. قواعد کش

- **کلید کش:** نام نرمال‌شدهٔ دامنه.
- **چه چیزی ذخیره می‌شود:** فقط پاسخ `OK` از Upstream که TTL آن بزرگ‌تر از صفر است (IP، TTL و لحظهٔ دریافت).
- **چه چیزی ذخیره نمی‌شود:** `NOT_FOUND`، `SERVER_ERROR` و پاسخ‌های فهرست‌ها (`AD_BLOCK` و `SANCTION`).
- **ثانیه‌های باقی‌مانده:** TTL منهای ثانیه‌های گذشته از لحظهٔ ذخیره (به‌صورت عدد صحیح). ورودی تا وقتی معتبر است که باقی‌مانده حداقل ۱ باشد؛ در غیر این صورت منقضی است، هرگز استفاده نمی‌شود و درخواست بعدی دوباره به Upstream می‌رود و ورودی را جایگزین می‌کند.
- **کش خاموش:** اگر `cache_enabled=false` باشد، کش نه خوانده می‌شود و نه نوشته می‌شود.
- **اولویت:** کش فقط بعد از بررسی فهرست‌ها مراجعه می‌شود؛ پس تغییر فهرست‌ها هرگز با کش نادیده گرفته نمی‌شود.
- زمان‌سنجی با `time.monotonic()` انجام می‌شود تا تغییر ساعت سیستم روی TTL اثر نگذارد.

## 11. مدیریت خطا

| موقعیت | رفتار برنامه |
|---|---|
| ورودی نامعتبر یا خالی | `INVALID_INPUT` و ادامهٔ برنامه |
| Upstream خاموش است یا مهلت تمام شد | `SERVER_ERROR` پس از حدود `upstream_timeout_sec` ثانیه و ادامهٔ برنامه |
| پاسخ نامفهوم یا IP/TTL نامعتبر از Upstream | `SERVER_ERROR` و ادامهٔ برنامه |
| دامنهٔ فهرست‌ها در زمان قطع بودن Upstream | بدون تماس با Upstream پاسخ داده می‌شود |
| خط نامعتبر در فایل فهرست | چاپ `Warning` و ادامهٔ برنامه |
| خطای پیکربندی | چاپ `Config error: ...` و توقف برنامه |

## 12. توضیح ماژول‌ها

### `config.py`
- خواندن `config.txt` و ذخیرهٔ مقادیر در دیکشنری `config`.
- نادیده گرفتن خطوط خالی و توضیح (`#`)؛ جدا کردن کلید و مقدار با `=` و حذف فاصله‌های اضافی.
- بررسی وجود کلیدهای الزامی؛ بررسی IPv4 بودن آدرس‌ها، بازهٔ پورت، مثبت بودن TTL و مهلت، و مقدار `true`/`false` برای کش.
- بررسی وجود دو فایل فهرست و ساخت مسیر کامل آن‌ها.

### `domain_utils.py`
- `normalize_domain`: حذف فاصله‌ها، تبدیل به حروف کوچک و حذف یک نقطهٔ پایانی.
- `validate_domain`: اعتبارسنجی نام طبق بخش ۷.
- `get_ad_list`: در صورت تطبیق دامنه با فهرست تبلیغاتی `sinkhole_ip` را برمی‌گرداند، در غیر این صورت `None`.
- `get_sanction_list`: همان منطق برای فهرست تحریم با خروجی `proxy_ip`.

### `load_domain_list.py`
- خواندن یک فایل فهرست، رد کردن خطوط خالی و توضیح، اعتبارسنجی و نرمال‌سازی هر ورودی، حذف موارد تکراری و چاپ `Warning` برای خط‌های نامعتبر.

### `dns_cache.py`
- کلاس `DNSCache` با متدهای `add`، `get`، `remove_expired` و `clear`.
- ذخیرهٔ IP، TTL و لحظهٔ دریافت؛ محاسبهٔ ثانیه‌های باقی‌مانده و حذف ورودی‌های منقضی.
- رد کردن IP نامعتبر و TTL صفر یا منفی هنگام ذخیره.

### `request_manager.py`
- کلاس `RequestManager`: اجرای گام‌های ۲ تا ۶ جدول بخش ۶ (اعتبار، نرمال‌سازی، فهرست تبلیغاتی، فهرست تحریم، کش).
- در صورت نیاز به Upstream، وضعیت `UPSTREAM_REQUIRED` را برمی‌گرداند.
- `save_upstream_response`: ذخیرهٔ پاسخ معتبر در کش (فقط اگر کش روشن باشد).
- `log_request`: افزودن یک سطر به `log.txt`.

### `UDP_Socket.py`
- کلاس `UDPClient`: ارسال `QUERY <domain>` روی UDP، دریافت و تفسیر پاسخ، و تبدیل هر خطا یا مهلت پایان‌یافته به `SERVER_ERROR`.

### `main.py`
- چاپ `DNS Proxy ready.`، بارگذاری فهرست‌ها، حلقهٔ خواندن ورودی از کنسول، فراخوانی `RequestManager` و `UDPClient`، و چاپ بلوک پنج‌خطی نتیجه.


## 13. تست‌ها

**تست‌های پذیرش (T1 تا T13):** خروجی کنسول این تست‌ها در `test_results.txt` آمده است. T1 تا T12 پشت‌سرهم در یک اجرای تازه و T13 با پیکربندی تغییریافته (`sinkhole_ip=10.0.0.1` و `cache_enabled=false`) انجام شده است. برای تست‌ها فقط از دامنه‌های آزمایشی `example.com`، `example.net` و `example.org` استفاده شده است.

**تست‌های واحد:** هر فایل را جداگانه با دستور زیر اجرا کنید:

```

python request_manager_test.py
```

| فایل | موضوع |

### فایل لاگ (B4)

برای هر درخواست دامنه یک سطر به انتهای `log.txt` اضافه می‌شود. ستون‌ها با `|` جدا می‌شوند: زمان، دامنه، Source، Status، IP و TTL (در نبود مقدار، `-`). فایل در پوشه‌ای ساخته می‌شود که برنامه از آن اجرا شده است. نمونه:

```
2026-11-20 18:45:52 | normal.example.net | UPSTREAM | OK | 198.51.100.7 | 5
2026-11-20 18:45:55 | normal.example.net | CACHE | OK | 198.51.100.7 | 1
2026-11-20 18:49:01 | missing.example.net | UPSTREAM | NOT_FOUND | - | -
2026-11-20 18:57:14 | bad domain.com | NONE | INVALID_INPUT | - | -
```
**### (B1) دستور `stats`**

کاربر با وارد کردن دستور `stats` می‌تواند آمار درخواست‌های پردازش‌شده را مشاهده کند. این آمار شامل تعداد کل درخواست‌ها، تعداد درخواست‌های مربوط به هر دسته (`AD_BLOCK`، `SANCTION`، `CACHE` و `UPSTREAM`) و همچنین تعداد درخواست‌های ناموفق یا دارای خطا (`ERRORS`) است.
اطلاعات آماری با خواندن و تحلیل فایل `log.txt` محاسبه می‌شوند.

**### (B3) دستور `cache`**

کاربر با وارد کردن دستور `cache` می‌تواند دامنه‌های موجود در کش را به همراه آدرس IP ذخیره‌شده و TTL باقی‌مانده آن‌ها مشاهده کند. در این بخش فقط ورودی‌هایی نمایش داده می‌شوند که هنوز منقضی نشده‌اند و مدت اعتبار آن‌ها به پایان نرسیده است.

** ###سقف ظرفیت کش : (B5)**
در این قابلیت، برای جلوگیری از افزایش بیش از حد تعداد ورودی‌های ذخیره‌شده در کش و مدیریت بهتر حافظه، امکان تعیین حداکثر ظرفیت کش فراهم شده است.
   مشخص شده.config.txtدر فایلentries_max_cacheحداکثر تعداد ورودی‌های قابل ذخیره در کش از طریق پارامتر
   هنگام اضافه شدن یک ورودی جدید به کش، تعداد ورودی‌های موجود بررسی می‌شود
   اگر ظرفیت کش باقی مانده باشد به کش افزوده میشود در غیر اینصورت اولین عنصر صف را که تایمش تمام نشده باشه پاک میکند
